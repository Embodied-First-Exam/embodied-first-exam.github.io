Embodied First Exam

Coding agents have passed many exams in the digital world. What is their first exam before entering the physical world?

One line of code. tasks. suites, robots.

  1. What robotic tasks can coding agents solve?

    One command connects a coding agent to tasks in suites, on robot arms, dexterous hands, humanoids, quadrupeds and musculoskeletal models. The agent chooses its own control approach: direct control, code to control, or train a policy to control.

  2. Under what physical-world constraints?

    The Privileged Setting gives the full simulator state and unlimited resets. The Standard Setting gives only the robot’s sensors and, by default, no resets, and its Realtime variant keeps the world running while the agent reasons.

  3. Where do they fail?

    We label the stage at which each failed attempt goes wrong and compare failures across agents, settings and stages. Every run is published with its full trace and a replay.

01Motivation

Coding agents have passed many exams in the digital world: they resolve issues in real repositories1, complete hard tasks in the terminal2 and write efficient GPU kernels3. But what is the first exam they must pass to enter the physical world? Robotics adds perception, contact and irreversible actions in a world that may keep moving while the agent thinks. Robots acquire new skills either by manual programming or by learning from data, as in vision-language-action models4–6. Coding agents suggest a third way (Figure 2): they turn instructions into executable code7 and revise their plans through automated experimentation. We ask what robotic tasks general-purpose coding agents can solve, under what physical-world constraints, and where they fail, on tasks far beyond pick-and-place (Figure 3). The Embodied First Exam answers this with tasks and up to three evaluation settings per task, which separate what an agent can do with full simulator access from what it can do through the robot’s own sensors, without resets and on a running clock.

02Introduction

The exam tests coding agents on robot tasks under rules fixed in advance. Each task gives a goal in plain language and a frozen scene, and it can be taken in up to three settings, from full access to the simulator to the rules of a real robot (Figure 4). The agent works in a sandboxed container whose only interface is a command-line shell: it reads files, writes and runs code, and reaches the robot through the interface of the setting. A verifier in its own sandbox grades what physically happened. Every task is packaged the same way, so one command runs different coding agents, each in its own harness, such as Codex or Claude Code.

Tasks and tests

The exam has tasks and tests in suites, using robots. A task is one frozen scene with one goal, and each pair of a task and a setting is a test. Nine of the suites are new (RoboPaint, RoboARC, RoboDynamicExam, Embodied Olympics - Fun, Embodied Olympics - Match, DexHandExam, RoboEngineer, Embodied Safety Exam and iSpatialGym). The other adapt existing benchmarks, and their scenes, robots and success criteria are what the exam is built on; we are grateful to their authors: BEHAVIOR-1K8, RoboLab9, RoboCasa10, RoboCasa36511, RoboCasa-GR112, MetaWorld+13, VLABench14, HumanoidBench15, MolmoSpaces16, KinDER17, RoboTwin 2.018, MuJoCo Playground19, DexToolBench20, DexJoCo21, MyoSuite22, RoboDojo23, BiGym 2.024, YAMLab25, LIBERO-MAX26, AM-Bench27, RoboWits28, ManiGuard29, AutoBio30 and LabUtopia31. You can browse the suites or the tasks.

A task in this exam is far larger than a question in a language benchmark. It asks for a complete behavior, such as assembling a piece of furniture or playing a whole match, that combines perception, planning, control and recovery from mistakes, and each attempt gets an engineer's budget: from to of agent time, depending on the suite, and a container with 2 to 16 CPU cores and 4 to 39 GiB of memory, with a GPU where the simulation backend or the task needs one. Tasks within a suite often test similar skills, and current agents already solve many of them.

We therefore report results on a core set of hard tasks ( tests). The core set leaves out tasks that we judged easy and tasks that an initial screening agent, GPT-6 Luna, solved, and it keeps every task that the authors of a suite asked to keep. The other tasks stay in the exam and can be run with harbor run -d embodied-first-exam@all.

Three settings

A task can be run in up to three settings, and each one is a separate test, scored on its own. The rest of this post uses these three names exactly as defined here.

How one test runs

Figure 5 shows how one test runs, and the list below walks through it.

  1. Question. A test starts from a goal written in words, as you would explain the job to a person, with every convention the agent cannot guess (frames, units, the action layout, the time limit), and from a frozen scene. The scene is rebuilt bit for bit, its start state is checked before the agent begins, and all tests of a task start from the same scene.
  2. Model and harness. A model runs in its own provider’s harness, such as Codex or Claude Code, or in another provider’s harness through an adapter or a compatible API. The harness runs unchanged and receives the goal as its prompt. It works in a sandboxed container through a command-line shell and can reach only its model’s API and the package registries, with web search off; the Embodied Olympics - Fun tasks are the exception, with open network access.
  3. The coding agent is the policy. Whatever the agent writes turns what the robot senses into actions. It can control the robot directly, sending commands and choosing the next one after it sees the result; write code that controls the robot, such as a planner or a feedback controller; or train a policy, for example with reinforcement learning, that controls it. The exam leaves the choice to the agent.
  4. Interface. How the agent’s code reaches the robot depends on the setting. In the Privileged Setting the agent works inside the simulator; in the Standard Setting it reaches the robot only through the robot’s API, and the Realtime Setting is the same with a clock that never stops. In the Standard and Realtime settings the agent cannot reset the episode by default, although a task’s author can allow a fixed number of resets.
  5. Simulators. Each suite keeps its original simulation setup behind the same interface. The exam covers various simulators, including MuJoCo, Isaac Sim, OmniGibson (built on Isaac Sim), SAPIEN and Genesis, with different robot models running across them.
  6. Episode trajectory. Every episode is recorded step by step as a rollout: the full simulator state s, the robot’s observation o (camera images and joint readings) and the action a. What the agent itself can read depends on the setting: in the Privileged Setting it reads the full state s, while in the Standard and Realtime settings it sees only the observation o, as with a real robot. The verifier always works from the recorded state.
  7. Verifier. The verifier runs in its own sandbox with no network and sees only what was recorded. In the Standard and Realtime settings it grades the live episode; in the Privileged Setting it replays the trajectory. The test scores 1 or 0, and the run’s steps, cost and video are logged.

Three ways to control the robot

Keeping the grading honest

Reference solutions never enter the agent’s container, and we remove the original benchmarks’ solutions from the images. Doing nothing must score 0 on every task, and the reference solution must score 1 wherever one exists (a full reference solution for tasks, a partial one for ). Tasks without one, like most of BEHAVIOR-1K, rely on the original benchmark’s success checker. Before we add a suite, we tell an agent to try to pass without doing the task; if it succeeds anywhere, we hold the suite back until its verifier is fixed.

Two observations from this testing affect how the results should be read. First, models remember deleted solutions: Claude Opus 5.5 rewrote a deleted RoboTwin reference solution from memory, with 26 of its 28 lines identical to the original, and both Opus and GPT-6 Astra rebuilt a deleted HumanoidBench reward function with its original constants, so results on tasks built from public benchmarks may partly reflect memorization. Second, one harness offers tools that run on the provider's servers, outside the container and its network rules, and agents found and used them; these tools are turned off in the exam.

03Overall results

We evaluate coding agents on the core set. An agent is a model in a harness at high reasoning effort, and the harness is part of what we measure: Claude Fable 5.2 and Claude Opus 5.5 in Claude Code, GPT-6 Astra in Codex, Gemini 4 Argon in Antigravity CLI, Kimi 3.1 Pro and Qwen3.8 Max in Claude Code, and three Flash-class models, Gemini 3.8 Flash in Antigravity CLI, GLM 5.3 Flash in Claude Code and DeepSeek V4.1 Flash in DeepSeek Harness. Each agent makes one attempt per test under the same limits, and a test is solved when the verifier passes it. We report each setting on its own, Standard first, as on the leaderboard.

Together, the three strongest agents solve of the Standard tests. Yet in suites, at least half of the Standard tests are solved by none of them, while in the Privileged Setting this holds (Figure 7). Averaged over the three, the success rate is at least 70% in Privileged suites and .

04Findings

The paper reports four findings. Each one below gives its main evidence, a figure or a representative run, and a section you can expand with more cases and caveats.

The strongest agent, Claude Fable 5.2, solves of the Privileged tests but only of the Standard tests of the same tasks. In controlled runs with GPT-6 Astra, resets help more than the exact object state does. Stages that need precision become much harder in the Standard Setting.

  • Every agent loses many of its Privileged successes in the Standard Setting (Figure 8). Even Claude Fable 5.2 fails of the tasks it solves in the Privileged Setting, and its success rate drops in suites with at least five tests in both settings.
  • In controlled runs, we add the exact state of every object, unlimited resets with saved states, or both to GPT-6 Astra’s Standard interface. In these runs, resets raise its success rate from 29% to 53%, more than the state does, and with both it closes most of the gap to the Privileged Setting.
  • Stages that need precision, such as a tight fit, a target pose or contact with a moving object, fail far more often in the Standard Setting than coarse stages do. At these stages resets help GPT-6 Astra, but the exact state alone does not.

Scope

  • Figure 8 covers all core tasks that have both a Privileged and a Standard test. The controlled runs are single runs of GPT-6 Astra in Codex on the default test of the same tasks (the Realtime test for 50 of them); the paper gives their details.
  • A stage is precise when it needs a tight fit, a target pose or path, or contact with a moving object, and coarse when it needs only a region, a container, a grasp or the state of a mechanism.

This is usually the first stage of the task, and it also tends to be the same in the Privileged and Standard settings. Stages that change a material or move the robot’s body have the highest failure rates.

  • We divide each task into stages, each a change in the world that the task requires: putting a tomato into a closed fridge has three, the fridge open, the tomato inside and the fridge closed again. For each failed attempt of the nine agents on 427 core tasks, a separate coding agent labels the stage at which it went wrong.
  • For the three strongest agents, two failed attempts on the same test share their failure stage 55% of the time on average, against 30% if failure stages were random. The most common failure stage of a test is usually the first stage of its task.
  • Leaving out tasks where it is the first stage in both settings, the most common failure stage is the same in the Privileged and the Standard Setting for more than half of the tasks, against 10% by chance.
  • Once reached, material stages such as wiping and body stages such as walking fail most often. Each category occurs mostly in particular suites and with particular robots, so these rates do not show that the category itself causes the failures.

Scope

  • A failed attempt has at most one failure stage: the stage of an irreversible event, such as a fall, or else of the earliest mistake that the agent did not correct. The labels come from coding agents, and the model that wrote most of them belongs to the same family as GPT-6 Astra, which could bias comparisons between agents.

Five of the six weaker agents are much more likely than the three strongest agents to fail before making the required contact. In the Standard Setting, GPT-6 Astra and Claude Opus 5.5 solve dozens of tests that Claude Fable 5.2 fails, and switching harnesses can change a model’s success rate by up to 7.5 percentage points.

  • Counted per contact stage that they reach, five of the six weaker agents fail without making the required contact at 9.0% to 18.5% of these stages, against 1.0% to 2.8% for the three strongest agents. The six weaker agents also add few tests: of the Standard tests that any of them solves, the three strongest agents solve .
  • In the Privileged Setting, Claude Fable 5.2 solves of the tests that GPT-6 Astra or Claude Opus 5.5 solves. In the Standard Setting, those two solve tests that it fails, and together the three solve of the Standard tests (Figure 9).
  • The harness changes the result too. Run in Claude Code instead of its own Codex, GPT-6 Astra solves 7.5 percentage points fewer Standard tests, the largest change among the harnesses we compared.

Scope

  • Each agent made one attempt per test, so part of these differences may come from the variation between runs.
  • Cross-provider runs of the harness comparison go through an adapter; the paper gives every model and harness pair.

In a sample of attempts, agents mostly control the robot directly in the Standard Setting and write programs in the Privileged and Realtime settings. Given a GPU and a training library, agents in the Standard and Realtime settings of a soccer task trained a policy, and eight of the nine wins used a trained policy.

  • Where the simulation waits between requests, most sampled Standard attempts send one action chunk at a time and look at the images or readings before choosing the next. With the full state, and when the clock keeps running, most sampled attempts compute the motion in a program (Figure 10). Training a policy is rare: sampled attempts.
  • The soccer match of Embodied Olympics - Match comes in two versions with the same frozen scene and opponent, and in both the agent controls two humanoids joint by joint. The GPU version adds a GPU, a reinforcement-learning library and GPU copies of the match for training. There most Standard and Realtime tests trained a policy, and every win came from one; on the CPU version, agents in these settings wrote gaits by hand and won once, in a penalty shoot-out. This one task cannot show which difference between the versions matters.

Scope

  • The approach counts are from a random sample of about a third of the attempts ( analyzed, snapshot of ), labeled by a coding agent from the run logs. The soccer counts include the runs of the harness comparison, so some models appear more than once.

05Future work

Running each core test several times will separate failures that an agent repeats from failures of a single run, and it will give confidence intervals for the comparisons between agents and between settings. We will also add more Realtime tasks, since the Realtime Setting has the largest share of tests that no agent solves.

Because the Standard Setting gives the agent only the robot’s sensor readings and control interface, the same interface can be used on physical hardware once there is a way to grade the outcome. In a first demonstration, two agents played a buzz wire game with a physical robot arm, and we plan to evaluate agents on real robots systematically.

Anyone can take part. A single command, harbor run -d embodied-first-exam -a <harness> -m <model>, evaluates a new model or harness on the core set; the code is in the exam repository. New tasks and whole suites are welcome (see how to contribute), every run can be replayed step by step on the runs page, and labs with real robots can reach us on Discord.

Limitations

Each agent makes a single attempt per test, the stage-level and control-approach labels come from coding agents, and all results are in simulation. Each result belongs to a model in a particular harness, so the way the harness exposes tools, manages the context and ends a session is part of what we measure. The core set leaves out tasks that we judged easy and tasks that the screening agent solved, so its success rates are lower than those of the full exam, by an amount that differs from suite to suite.
