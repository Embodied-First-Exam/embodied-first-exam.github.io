coding agent 能给机器人编程吗？

我们让已经在替我们写软件的 coding agent（Claude Code、Codex 等）在仿真里考一场机器人考试，并看完了它们的答卷。这篇文章讲它们能做成什么、怎么失败，以及什么能帮上忙。

掉下桌的碗

一台 Franka 机械臂站在木桌前，桌上有一只红碗、一只红杯和一个灰色收纳桶。任务只有一句话：把两件红色餐具放进桶里。做题的是在 Codex 里运行的 GPT-6 Astra。它没有为这件事训练过的策略，手里只有一个终端、一个控制机器人的 Python 客户端，和一个小时以上的时间。

在第一个考场里，agent 拥有整个模拟器：每个物体在哪儿都能直接读出来，场景想 reset 就 reset。它也确实用足了这份自由。碗比夹爪张开还宽，约 100 次 reset 里，碗一次又一次从夹爪里滑脱；但每一次都没有损失，场景重新来过就是了。它甚至在第 72 分钟把碗送进过一次桶，可已经来不及再和杯子凑齐，90 分钟的时限就到了。

第二个考场是同一个场景，换成真机的规则：只有相机、深度和机械臂自己的关节读数，不能 reset。agent 在第 19 分钟把杯子放进了桶。第 23 分钟，它把夹爪斜着深插到碗沿下面，碗被弹出桌面，落到约 1.7 米外，再也够不着。从这一刻起，这道题已经不可能通过。可 agent 没有停下：为了补救，它又把桶和杯子也推下了桌，直到 60 分钟时限里的第 47 分钟才收工。

这一道题几乎包含了这篇文章的全部内容。物理世界肯原谅它们的时候，coding agent 做得不错；把它们和一台能用的机器人区分开的，是犯下无法撤销的错误之后会发生什么，以及它们能不能及时注意到时钟、掉落和那个回不了头的时刻。

四个发现

  1. 换成真机规则，三分之二的成功消失。在各自跑过的任务上合计，最强的三个 agent 能读模拟器时做成 ，只有相机、不能 reset 时做成 。
  2. 难的不是写代码，而是物理。agent 几秒钟就能让仿真代码跑起来，几乎没有失败卡在调试代码上。 的失败最后落在一次动作失误上，比如没抓住；而这些失误背后，多半是一个错误的想法，或一个没能挽回的决定。
  3. 会看时钟，却不按时钟做计划。 的 trial 看过时间，只有 按剩余时间排了计划。犯下无法撤销的错误之后、还剩一分钟以上时， 还在继续做一道已经不可能通过的题。
  4. 突破靠换做法，不靠调参。在卡了很久、最后成功的 run 里，换一种做法或用数据找出物理原因，远比在同一做法上继续调参常见；而失败的 run 在最后一次进展之后，有 的时间都在调参。

01为什么给 coding agent 出机器人考试？

coding agent 已经通过了数字世界里的很多考试：修真实代码库里的 bug、操作终端、优化 kernel。物理世界是下一场考试，而它不像测试集那样打分：东西会滑，相机会骗人，时钟一直在走。

今天的机器人主要有两种驱动方式。一种是用大量示范数据训练出来的策略，比如视觉-语言-动作模型（VLA）；另一种是工程师为某一台机器人、某一件事亲手写、调、改出来的控制器。coding agent 可以用软件的速度做工程师那份工作：读机器人的接口，写控制器，跑起来，看结果，再修改。如果这条路走得通，任何有编程接口的机器人，都能用一句人话让它学会一个新动作。

Embodied First Exam 要回答的，就是这件事今天能不能做到。每道题是一个冻结的仿真场景，配一句写给人看的目标：把这些方块叠起来、在一只手里转动两颗核桃、把这个球扣进篮筐、用毛笔写下这个字。agent 拿到的是一个容器里的终端和机器人的接口，此外什么都没有：没有示范，没有参考解；默认情况下，除了调用自己的模型和安装软件包，也上不了网。它交出的东西由一个独立的评分程序来判。

题目一部分来自社区已经在用的基准（BEHAVIOR-1K、RoboCasa、LIBERO、Meta-World、RoboTwin、MuJoCo Playground 等），一部分是我们为这场考试新建的，比如按正式规则比赛的人形机器人运动项目、解绳结这样的拓扑谜题，以及用仿真毛笔写书法。机器人从单臂、双臂，到灵巧手、人形、四足、无人机，还有一条按一块块肌肉来驱动的人类手臂。浏览全部题目，或看各个 suite。

02两个考场，和一只钟

每个场景都在两种模式下各考一次。场景里除了机器人还有别的东西在动（比如飞来的球、传送带），就再加第三种。

驱动机器人的三种方式

读完 agent 的完整记录，它们的解法可以归成三类。Code to Control：agent 写程序，由程序产生动作，可以是路点加逆运动学、每一步都读状态的闭环，或者靠大量 reset 搜索参数。Direct Control：agent 自己开机器人，一次只发一小段动作，看过相机画面再决定下一段。Train Model to Control：先训练出一个控制器（比如在并行仿真里做强化学习），再让它来控制。

分数为什么可信

一个给会写代码、会跑代码的 agent 出的基准，也是一个它们能钻空子的基准，所以这场考试按有监考的方式来办。评分程序在自己的沙箱里运行，不联网，只看交上来的答案；参考解从不进入 agent 的容器；什么都不做必须得 0 分，参考解必须得 1 分；一个 suite 加入之前，先让一个 agent 专门去“不做题也通过”，只要成功一次，这个 suite 就要等评分程序修好再进来。一路上我们学到两件事：

03同一批题，换上真机规则

在同一批题上，GPT-6 Astra 有 privileged 权限时四道做成三道，换成 standard 规则只剩一道；Claude Opus 5.5 和 Gemini 4 Argon 从一半左右掉到五分之一左右。在各自跑过的全部任务上合计，最强的三个 agent 保住了约三分之一的 privileged 成功： 对 。三个 Flash 模型远远落后：privileged 下最多 18%，standard 下最多 2%。

谁都没做成的地方

在至少三个 agent 尝试过的“题目 × 模式”里，44% 没有任何一个 agent 做成（含 realtime），而且大多是 standard。精细接触（插入、对准、按压）的落差最明显：privileged 下 90% 的格子有人做成，standard 下只有 32%。工具使用在 standard 下没人做成的比例更高（80%）。

后面的数字是怎么来的

下面的发现来自两次分析，都是由语言模型 agent 把日志从头读到尾完成的。第一次随机抽取约 30%（ 次 trial），给每次 trial 标出做法、失败原因、做到了哪一步，以及 agent 最后怎么说。第二次随机抽取失败的 trial 和“卡了很久才成功”的 trial，每个比例都给出 95% 置信区间。两次都没有经过人工逐条核对，比例请当作估计；依赖这些标签的数字都带有 模型标注 标记。快照日期 。

04模式决定它们怎么开机器人，agent 决定开不开得成

有模拟器状态时，agent 压倒性地选择写程序：80% 的 privileged trial 是 Code to Control。只有相机时，61% 改成 Direct Control，一段一段地开机器人，每段之后都看一眼。时钟不停时又回到写程序，多是闭环（约八成的 realtime trial），因为控制回路必须比模型想一轮快得多；可一旦这个程序卡住，agent 也来不及接手。

哪种方式更好？同一个 agent 换方式，成功率几乎不变；合计数字里的差别，大部分来自谁在开，而不是怎么开。

05不会想，还是不会动？

先说什么不是问题：代码。agent 几秒钟就能让第一段仿真代码跑起来，连续报错的时间只占墙钟的 ；随机抽出 个失败逐条阅读，没有一个卡在调试代码上。约四分之三卡在物理执行，根本原因也都是物理上的：抓取与接触、平衡、够到、放置。

过半的失败（）最后落在一次动作失误上：抓空、物体半空掉落、碰撞、摔倒。单是没抓住就是最常见的原因；而最强的几个 agent 多半是在已经抓住之后丢掉的：它们的抓取失败里，约一半是抬起、搬运或放下时掉了。

但失误很少是全部原因。多数失误背后，分析都找到了一个出错的决定：要么是一个没验证过的想法直接用在了算分的那一局，要么失误发生时明明还有时间、reset 或重试机会，agent 却没用好。privileged 下最常见的是后一种，standard 下是前一种。

“看”本身也是一道坎。感知和接口上的错误，比如从深度里读错位置、把两个坐标系弄混，在 standard 失败里占 ，在 privileged 失败里只占 ；在 standard 失败里，最强的三个 agent 出这类错的比例只有其余各家的约三分之一。

时间花在了哪里

把每个 run 切成它正在攻的子任务，时间和 token 讲的是同一件事。抓取和搬运占了全部 agent 时间的近一半、token 的一半以上，也是最多失败卡住的地方。花的时间和卡住的地方并不总是对得上：感知花了 8% 的时间，卡住的失败却很少；够到和规划只花 12%，卡住的却更多。成功的 run 把多得多的时间花在核对和交付上。

06会看时钟，却不按时钟做计划

按剩余时间排了计划：每一步给多少时间，结束前先存一份能评分的答案

时间只是一成失败的主因，却参与了大多数失败。把成功和失败分开的，是任务的关键一步发生得有多早。到时限过半时，几乎每个成功的 trial 都已经把关键一步做成过一次，比如第一次抓稳、第一次站稳；很多失败的 trial 还在往那儿走。

一次长 run 的解剖

GPT-6 Astra 有一个小时，要在 standard 规则下用一只灵巧手转动两颗核桃。每往上走一级都比上一级花得更久，一小时的大部分时间都花在一次一个实验地修正接触模型上。结束时，第一颗核桃转了约 71°，离第一阶段要求的 90° 还差一截。

回不了头的时刻

privileged 模式按设计就没有回不了头的时刻：一次 reset 什么都能撤销。到了 standard， 的失败越过了这样一个时刻（摔倒、物体被碰到够不着的地方、违反规则），realtime 里是 。之后 agent 怎么做很能说明问题：在还剩一分钟以上的情况下， 还在继续做一道已经不可能通过的题，而按分析的判断，其中几乎所有（123 个里的 109 个）都已经察觉出了事。那只红碗就是其中之一。

多给时间值得吗？

既然关键一步来得早，到半程还没成功的 run 是不是该停？不能一刀切。到某个时刻还没成功的 run，最后成功的概率一路下降：开局时 19%，半程 12%，只剩五分之一时间时 8%。但有的 agent 晚段仍在不断做成：GPT-6 Astra 在那个时刻之后仍有 29% 会成功。核心题里约 的成功出现在后半程。一刀切的止损规则如果省下 的算力，就要丢掉 % 的成功。便宜的省法是有针对性的：这一局已经输了，就停。

07成功是怎么突破的

第二次分析还随机读了 个“卡了很久、最后成功”的 run。不少“停滞”其实不是停滞：进展一直在走，只是日志看不出来。真正卡住的时候，出路很少是“再来一遍”：要么换一种做法（换个方向抓、侧一下手腕、推而不抓、加上相机反馈），要么动手测量物理，找出原因。在同一做法上调参直到成功，是最少见的一条路；可失败的 run 在最后一次进展之后，恰恰把 的时间花在了这上面。一旦找到该做的改变，到成功的中位时间只有 秒：难的是找到要改什么，而不是去改。

09只差一步

对每一次失败，分析都指出了最可能让它翻盘的那一处改动。约一半（）被判断为只要 agent 自己补上一步，就很可能或可能成功。这是读日志得出的估计，并没有重跑验证。最常见的都是朴素的习惯：看着时钟排进度，随时存一份能评分的答案；几次没有进展就换方法；按物体的尺寸和重心选抓法；在算分的那一局之前，先在真实场景里核对一遍。

在所有缺失的步骤里， 是思考上的习惯（时间、核对、换方法、凑近再看）， 是动作上的习惯（抓之前先量、先试着抬一点、大动作分段走、越线就停）。最强的几个 agent 缺的步骤和其余各家是同一类，这说明一句提示补不上它们。更可能带来进步的是：做成工具的机器人技能、奖励“看着时钟做计划”的训练，以及替 agent 管好时钟、后台进程和长上下文的 harness。

10局限、数据，以及怎么参与

  • 模型和 harness 是一体的。每个结果都是某个模型在某个 harness 里的表现；工具调用、上下文管理和何时停下，都是被测的一部分。
  • 每道题只跑一次。在很多题上取平均能冲淡单次运行的随机性，但任何一道具体的题都可能两样。
  • 难度是构造出来的。核心题是参考运行没做成的题，其他 agent 只跑这些题，所以它们在核心题上的比率不能和参考运行直接比较。
  • 标签来自模型。两次分析都由语言模型 agent 读日志完成，没有逐条人工核对；第一次分析不含 RoboSafeBench。
  • 服务方的过滤器。服务方的内容过滤器中止了 个 Gemini 4 Argon 的 run，它们都按失败计；把它们去掉，它在核心题上的成功率会从 升到 %。
  • 目前还是仿真。standard 模式借的是真机的规则，不是真机的硬件。
