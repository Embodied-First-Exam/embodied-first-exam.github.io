Can a coding agent program a robot?

We gave the coding agents that already write our software (Claude Code, Codex and their peers) a robot exam in simulation, and watched them sit it. Here is what they can do, how they fail, and what would help.

Embodied First Exam TeamOctober 2026 EN中文

The bowl that fell off the table

A Franka arm stands at a wooden table with a red bowl, a red cup and a grey bin. The instruction is one sentence: put both red dishes in the bin. The agent, GPT-6 Astra running in Codex, has no trained policy for this. It has a terminal, a Python client for the robot, and an hour or more.

In the first room the agent owns the simulator: it can read where every object is and reset the scene whenever it likes. It used that freedom. The bowl is wider than the gripper opens, and over about 100 resets it slipped out of grasp after grasp. Each time nothing was lost; the scene simply came back. It even got the bowl into the bin once, at minute 72, too late to pair it with the cup before its 90 minutes ran out.

In the second room the same scene runs under a real robot’s rules: cameras, depth and the arm’s own joint readings, and no reset. The agent put the cup in the bin at minute 19. At minute 23, tilting the gripper deep under the bowl’s rim, it flicked the bowl off the table; it landed about 1.7 m away, out of reach. The task was lost at that moment. The agent did not stop: trying to recover, it pushed the bin and the cup off the table as well, and ended the session at minute 47 of its 60.

This one task holds most of this post. Coding agents are good at the physical world when it forgives them. What separates them from a working robot is what happens after a mistake that cannot be undone, and whether they notice the clock, the drop or the point of no return in time.

In four findings

  1. Real-robot rules cost two-thirds of the successes. Pooled over the tasks they ran, the three strongest agents solve when they can read the simulator and with only cameras and no resets.
  2. Writing the code is not the hard part; the physics is. Agents have simulator code running within seconds, and almost no failure gets stuck in debugging. end in a motor slip such as a lost grasp, and behind most of those sits a wrong idea or a decision that did not recover.
  3. Agents watch the clock but don’t plan with it. of trials checked the time; planned by it. After a mistake that could not be undone, with more than a minute left, kept working on a task that was already lost.
  4. Breakthroughs come from changing the approach, not tuning it. Among runs that stalled and then succeeded, switching approach or diagnosing the physics from data beat tuning the same approach by a wide margin; failures spent of their time after their last progress tuning.

01Why give coding agents a robot exam?

Code agents have passed many exams in the digital world: fixing real repositories, driving terminals, tuning kernels. The physical world is the next one, and it does not grade like a test suite. Objects slip, cameras mislead, and the clock keeps running.

Robots today are driven in two main ways. One is a policy trained on many demonstrations, such as a vision-language-action model. The other is a controller that an engineer writes, tunes and debugs for one robot and one job. A coding agent can do the engineer’s job at the speed of software: read the robot’s interface, write a controller, run it, look at what happened, and fix it. If that works, any robot with a programmatic interface becomes something you can ask for a new behaviour in plain language.

The Embodied First Exam asks whether that works today. Each question is a frozen simulation scene with a goal written for a person: stack these blocks, turn two walnuts in one hand, dunk this ball, write this character with a brush. The agent gets a terminal in a container with the robot’s interface, and nothing else: no demonstrations, no reference solution, and by default no internet beyond its own model and package installs. An independent verifier marks what it produced.

The questions come from benchmark suites the community already uses (BEHAVIOR-1K, RoboCasa, LIBERO, Meta-World, RoboTwin, MuJoCo Playground and more) and from suites we built for this exam, such as humanoid sports at official settings, topological puzzles like untying a knot, and Chinese calligraphy with a simulated brush. The bodies range from one arm and two-arm rigs to dexterous hands, humanoids, quadrupeds, drones and a human arm driven one muscle at a time. Browse every question or the suites.

Sitting the exam is one line with Harbor, and any agent with a terminal works unchanged:

02Two rooms and a clock

Every scene is sat in two modes. Scenes where something besides the robot moves, such as a thrown ball or a conveyor, get a third.

Three ways to drive a robot

Reading the agents’ transcripts, their solutions fall into three families. In Code to Control the agent writes a program and the program produces the actions: waypoints and inverse kinematics, a closed loop that reads the state every step, or a search over parameters across many resets. In Direct Control the agent drives the robot itself, one short chunk of motion at a time, looking at the cameras before deciding the next. In Train Model to Control it first trains a controller, for example with reinforcement learning in parallel simulations, and lets that drive.

Why the marks can be trusted

A benchmark for agents that write and run code is also a benchmark they can game, so the exam is run like one with a proctor. The verifier runs in its own sandbox without network and sees only the answer. Reference solutions never enter the agent’s container. Doing nothing must score 0 and a reference solution 1. Before a suite joins, an agent is told to pass without doing the task, and any success blocks the suite until its verifier is fixed. Two things we learned on the way:

Where nobody succeeds

Of the task-and-mode cells that at least three agents attempted, no agent solved 44% (realtime cells included). Most of them are standard. Precise contact (inserting, aligning, pressing) shows the gap most sharply: someone solves 90% of its privileged cells but only 32% of its standard ones. Tool use is unsolved even more often under standard rules (80%).

04The mode decides how they drive; the agent decides whether it works

Given the simulator’s state, agents overwhelmingly write a program: 80% of privileged trials are Code to Control. Given only cameras, 61% switch to Direct Control and drive the robot a chunk at a time, looking after each. A running clock pushes them back to code, mostly a closed loop (about four in five realtime trials), because the loop has to run faster than a model can think. When that program stalls, there is no time to take over.

Which way works better? Within one agent, the success rate barely changes with the way. Most of the difference between the pooled numbers is who is driving, not how.

05Thinking or moving?

Start with what is not the problem: the code. Agents have their first simulator code running within seconds, unbroken runs of errors take of the wall clock, and in a random sample of failures read one by one, not a single one was stuck at debugging code. About three in four were stuck in physical execution, and the root causes are physical: grasp and contact, balance, reaching, placement.

More than half of failures () end in a motor mistake: a grasp that misses, an object dropped mid-air, a collision, a fall. A lost grasp alone is the most common cause, and the strongest agents mostly lose objects they already hold: about half of their grasp failures are drops while lifting, carrying or placing.

But a slip is rarely the whole story. Behind most of them the analysis finds a decision that went wrong. Either an untested idea went straight into the attempt that counted, or there was still time, a reset or a retry left when the slip happened, and the agent did not use it well. With privileged access the second kind is the most common; under standard rules, the first.

Seeing is a problem of its own. Errors of perception and interface, such as positions misread from depth or two coordinate frames mixed up, cause of standard failures against of privileged ones, and among their standard failures the three strongest agents have them at about a third the rate of the rest.

Where the hours go

Splitting every run into the subtask it was working on shows the same picture in time and tokens. Grasping and carrying take almost half of all agent time and more than half of the tokens, and they are where most failures get stuck. Time spent and getting stuck do not always line up: perception takes 8% of the time but holds up few failures, while reaching and planning take 12% and hold up more. Successful runs spend far more of their time checking and delivering what they did.

Time is the main cause of only a tenth of failures, but it plays a part in most. What separates success is how early the task’s key step happens. By half the time limit, nearly every successful trial had already done it once, for example the first grasp that held or the first stable step; many failures were still getting there.

Anatomy of a long run

GPT-6 Astra had an hour to turn two walnuts in one dexterous hand, under standard rules. Each step up took longer than the last, and most of the hour went into refining a contact model one experiment at a time. It ended with the first walnut turned about 71°, short of the 90° the first stage asks for.

The point of no return

Privileged mode has no point of no return by design: a reset undoes anything. Under standard rules, of failures pass one (a fall, an object knocked out of reach, a rule broken), and in realtime . What agents do next is telling. With more than a minute left, kept working on a task that could no longer be passed, although almost all of them (109 of 123) had noticed what happened, by the analysis’s reading. The red bowl was one of them.

Is more time worth it?

If the key step comes early, should a run that has not succeeded by half time stop? Not across the board. The chance that a run not yet successful still succeeds falls steadily, from 19% at the start to 12% at half time and 8% with a fifth of the time left, but some agents keep converting late: GPT-6 Astra still succeeds 29% of the time from that point. About of core successes come in the second half. A blanket stop rule that saved of the compute would cost % of the successes. The cheap saving is the targeted one: stop when the episode is already lost.

07How the successes broke through

The second analysis also read a random runs that stalled for a long time and then succeeded. Many “stalls” were not stalls at all: progress was steady but invisible to the logs. Where an agent really was stuck, the way out was rarely more of the same. It switched to another approach (grasp from the other side, tilt the wrist, push instead of pick, add camera feedback), or it measured the physics and found the cause. Tuning the same approach until it worked was the rarest route; yet failed runs spent of their time after their last progress doing exactly that. Once the right change was found, success followed in a median of seconds: the hard part is finding what to change, not doing it.

09One step from success

For each failure the analysis named the single change most likely to have rescued it. About half () are judged likely or possibly fixable by one step the agent itself could have taken. That is an estimate from reading the logs, not a rerun. The most common are plain habits: plan by the clock and keep a gradeable answer saved; switch method after a few tries without progress; choose the grasp from the object’s size and centre of mass; check the result in the real scene before the attempt that counts.

Of all the missing steps, are habits of thought (time, checking, switching, looking closer) and are motor habits (measure before grasping, lift a little first, move in segments, stop when a limit is crossed). The strongest agents miss the same kinds of step as the rest, which suggests a prompt will not supply them. Progress is more likely to come from robot skills packaged as tools, training that rewards planning against a clock, and harnesses that keep the clock, background processes and long contexts in order on the agent’s behalf.

10Limits, data and how to take part

  • Model and harness together. Each result is a model in a particular harness; tool use, context handling and stopping are part of what is measured.
  • One trial per task. Averages over many tasks dilute the noise of single runs, but any one task can go either way.
  • Hard by construction. The core questions are those our reference run failed; other agents ran only those, so rates on them are not comparable with the reference run’s.
  • Labels by a model. Both analyses were done by language-model agents reading the logs and were not checked line by line; RoboSafeBench is not part of the first.
  • Provider filters. The provider’s content filter ended Gemini 4 Argon runs, which count as failures; leaving them out would raise its core success rate from to %.
  • Simulation, for now. The standard mode borrows a real robot’s rules, not its hardware.
