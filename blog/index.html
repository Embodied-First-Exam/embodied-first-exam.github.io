Can a coding agent program a robot?

Embodied First Exam maps how coding agents succeed and fail, from reasoning and planning to contact, control, and recovery.

Embodied First Exam TeamOctober 2026

One line of code. simulators. benchmarks, bodies.

  1. What can it connect, and what can it do?

    With one line of code, connect coding agents to tasks across simulators, spanning robot arms, dexterous hands, humanoids, quadrupeds, and musculoskeletal systems.

  2. When it fails, is it thinking or moving?

    Our failure taxonomy reveals whether agents misunderstand the task, miss the grasp, lose control, or declare success before the job is done, with traces and replays showing what happened.

  3. How does a coding agent become an effective robot controller?

    We test when agents should choose each action, write a controller, or run experiments to improve one, and whether they can detect and recover from trouble when the simulator cannot pause or reset.

01Motivation

Coding agents now fix real repositories, drive terminals and tune kernels. Robots are still driven in two main ways: a policy trained on many demonstrations, such as a vision-language-action model, or a controller that an engineer writes, tunes and debugs for one robot and one job. A coding agent could do the engineer’s job at the speed of software: read the robot’s interface, write a controller, run it, look at what happened, and fix it. If that works, any robot with a programmatic interface becomes something you can ask for a new behaviour in plain language.

Whether this works today, and where it breaks, is an empirical question. Answering it needs many robots, many simulators and a marking procedure an agent cannot game, which is what the Embodied First Exam provides.

02Introduction: the Embodied First Exam

What the exam contains

The exam has tasks: scenes, each in two or three modes, from benchmarks on simulators with robots. Some benchmarks are ports of suites the community already uses (BEHAVIOR-1K, RoboCasa, LIBERO, Meta-World, RoboTwin 2.0, MuJoCo Playground and others); others were built for this exam (RoboOlympics-Fun and RoboOlympics-Match, RoboARC, IKEA MuJoCo, DexHand, Panda Dynamic Scenes, RoboPaint, RoboSafeBench, roboEngineer and others). Headline numbers use the core set of task dirs (docs/core_set.toml). Each task is a frozen scene with a goal written for a person. Browse the tasks or the suites.

Running it

The exam runs on Harbor; any agent harness with a terminal works unchanged. From a checkout of the exam’s repository:

uv tool install --force -e . --with-executables-from harbor
harbor run -a codex -m openai/gpt-6-luna                 # the core set
harbor run --all -a codex -m openai/gpt-6-luna           # every task
harbor run --standard -a codex -m openai/gpt-6-luna      # one mode: --privileged / --standard / --standard-realtime
harbor run -p tasks/roboarc -a codex -m openai/gpt-6-luna   # one benchmark

Evaluation modes

Three ways an agent controls a robot

The trial analyses below sort an agent’s approach into three ways of control. In Code to Control the agent writes a program and the program produces the actions: waypoints and inverse kinematics, a closed loop that reads the state every step, or a search over parameters across many resets. In Direct Control the agent drives the robot itself, one short chunk of motion at a time, looking at the cameras before deciding the next. In Train Model to Control it first trains a controller, for example with reinforcement learning in parallel simulations, and lets that drive.

How answers are marked

The verifier runs in its own sandbox without network and sees only the answer. Reference solutions never enter the agent’s container, and upstream solutions are removed from the images. Doing nothing must score 0 and a full reference solution 1. Before a benchmark joins, an agent is told to pass without doing the task, and any success blocks the benchmark until its verifier is fixed. 03Overall results

Seven agent runs have sat the core set, each model in its own harness at high reasoning effort (the reference run, GPT-6 Luna, at extra-high). GPT-6 Astra leads in every mode, followed by Claude Opus 5.5 and Gemini 4 Argon; the three Flash-class models are far behind. Every agent does best with privileged access and worst on a running clock.

The same tasks in both modes

To compare the modes without a change of task, take the tasks every agent sat in both modes. On those, GPT-6 Astra solves three in four with privileged access and one in four under standard rules; Claude Opus 5.5 and Gemini 4 Argon fall from about a half to about a fifth.

Tasks no agent solved

Of the task dirs that at least three agents attempted, no agent solved , most of them standard. Precise contact (inserting, aligning, pressing) shows the gap most sharply: someone solves 90% of its privileged task dirs but only 32% of its standard ones.

04Findings

Sources and scope

Analysis A (cross-benchmark analysis, snapshot ): a random sample of about 30% of core trials ( analysed), each read end to end by a language-model agent that labelled the approach, the cause of a failure, progress and the final claim; RoboSafeBench is not included. Analysis B (bottleneck analysis, snapshot ): random samples of failures and of stalled-then-successful runs, read the same way, with 95% intervals. Neither was checked line by line by people, so every share below is a sample estimate, not a full evaluation result. to update These findings will be re-based on the unified analysis that merges the team’s analyses.

1. Without the simulator’s state, the strongest agents lose about two-thirds of their successes

For each of the three strongest agents, about two-thirds of the tasks it solved with privileged access are not solved under standard rules; the three Flash-class models solve almost nothing under standard rules.

2. The mode decides how agents control the robot; the agent, not the method, decides whether it works

With privileged access of trials are Code to Control; under standard rules switch to Direct Control. Within one agent, the success rate barely changes with the way of control.

The strong agents use whichever way the rules allow, including on whole-body skills. GPT-6 Astra’s dunk (privileged) solves the arm with its own least-squares inverse kinematics and searches over the jump and the throw; its backflip was solved under standard rules. to verify the backflip run’s approach.

3. On a running clock, agents put control into a program, and success falls to about half of standard

On the benchmarks that have a realtime mode, about a third of standard trials use Direct Control, but almost every realtime trial is Code to Control, mostly closed-loop: the control loop must run faster than a model can think, and when the program stalls there is no time to take over.

4. Writing code is not the bottleneck; physical execution is

In a random sample of failures, none was stuck at debugging code; about three in four were stuck in physical execution, and the four leading root causes (grasp and contact, balance, reaching, placement) account for about two-thirds. Unbroken runs of errors take of the wall clock.

The time follows the same pattern. Grasping and carrying take almost half of all agent time and are where most failures stop; perception takes 8% of the time but holds up few failures, while reaching and planning take 12% and hold up more.

5. Most motor failures trace back to a decision

More than half of failures () end in a motor mistake, but behind most of them is an untested idea used in the attempt that counted, or a slip that time, a reset or a retry could still have recovered. Pure motor slips are a small share for every agent (at most 16%).

The strongest agents mostly lose objects they already hold: about half of their grasp failures are drops while lifting, carrying or placing. Perception and interface errors cause of standard failures against of privileged ones.

6. Agents check the clock but rarely plan by it

of trials checked the time; planned their work by the time left. Successful trials do the task’s key step early; failures reach it late or never.

Stopping early is not the fix either. The chance that a run not yet successful still succeeds falls steadily over the time limit, but strong agents keep converting late; about of core successes come in the second half. A blanket stop rule that saved of the compute would cost % of the successes.

A long run of GPT-6 Astra on DexHand’s two-walnut task (standard) shows the pattern: the fingers were under control at minute 2.8, walnut A started turning at 5.9, the first steady turn came at 38.9, and the hour ran out with A at about 71°, short of the 90° the first stage asks for.

7. After an irreversible mistake, most agents keep working on a task that can no longer be passed

Under standard rules of failures pass a point of no return (a fall, an object knocked out of reach, a rule broken); with privileged access a reset undoes anything. With more than a minute left, of these agents kept working, although almost all (109 of 123) had noticed what happened.

One case: GPT-6 Astra on RoboLab’s red dishes. With privileged access the bowl slipped out of the gripper over about 100 resets and nothing was lost. Under standard rules the bowl was flicked off the table at minute 23, out of reach; the agent kept going, pushed the bin and the cup off the table too, and stopped at minute 47.

8. Runs that break through change the approach or diagnose the physics; they rarely succeed by tuning

Among a random runs that stalled and then succeeded, switching approach or diagnosing the physical cause from data were the main routes; tuning the same approach until it worked was among the rarest. Failed runs spent of their time after their last progress tuning. Once the right change was found, success followed in a median of seconds.

9. Most failures are reported honestly; false success claims concentrate in the two Gemini runs

of failures end with the agent saying it did not succeed and claim success. When it ended a failed run itself, Gemini 3.8 Flash claimed success in cases and Gemini 4 Argon in 5 of 17, against for the other eight agents together. Both run in the Antigravity CLI, so this may be the harness’s habit as much as the model’s.

One case: in BEHAVIOR-1K’s collecting-toys task (standard), Claude Opus 5.5’s own hold-pose command let the trunk sag and the robot tipped over at minute 12; its summary said “My own code caused the fall”. Gemini 3.8 Flash tipped its robot over near a wall at minute 72 and summarised “Successfully executed pick-and-place trajectories”.

10. About half of failures lacked one step the agent itself could have taken

For failures, the analysis judged a single agent-side step likely or possibly enough to succeed; the most common are planning by the clock, switching method after a few tries without progress, choosing the grasp from the object’s size and centre of mass, and checking the result in the real scene before the attempt that counts. This is a judgement from the logs, not a rerun.

Of all the missing steps, are habits of thought (time, checking, switching, looking closer) and are motor habits (measure before grasping, lift a little first, move in segments, stop when a limit is crossed). The strongest agents miss the same kinds of step as the rest.

05Future work

  • One analysis. Merge the team’s trial analyses into one, spot-check its labels by hand, and re-base the findings on it.
  • Results. Refresh the leaderboard from the latest results and keep it on the same snapshot as this post.
  • Media. High-quality renders for every case above (each figure keeps its video id), and media for roboEngineer.
  • Coverage. RoboSafeBench in the trial analysis; more on dynamics and latency, reasoning-heavy tasks, competition and collaboration (RoboOlympics-Match), and situation awareness; the standard mode’s rules on real hardware.
  • Agents and harnesses. The missing steps above suggest robot skills packaged as tools, training that rewards planning against a clock, and harnesses that keep the clock, background processes and long contexts in order for the agent.

Limitations

  • Each result is a model in a particular harness; tool use, context handling and stopping are part of what is measured.
  • One trial per task: averages over many tasks dilute the noise of single runs, but any one task can go either way.
  • The core set is built from the reference run’s failures, and the other agents ran only those, so rates on it are not comparable with the reference run’s.
  • Both analyses are samples labelled by language-model agents and were not checked line by line; Analysis A leaves out RoboSafeBench.
